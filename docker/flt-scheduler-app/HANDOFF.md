# 1-227 AB Flight Scheduler — Session Handoff Document

## 1. Project Summary

We are building and iteratively improving a web-based flight scheduling and mission management system for the 1-227 Attack Battalion (Army helicopter unit). The application handles the full lifecycle of a flight mission: creation by a scheduler, approval by an approver, closeout with actual times, and audit logging. It runs as a single Docker container, deployed on-prem or in a small Kubernetes cluster, and is accessed by ~10–50 concurrent users (pilots, crew chiefs, staff officers). The current version is **0.10.2-beta**. The codebase is a working production app — all future tasks are enhancements and bug fixes, not greenfield work.

## 2. Decisions Locked In

- **Language:** Python 3.12. No alternatives considered; already in production.
- **Framework:** Flask 3.0.3 with Flask-WTF 1.2.1 for CSRF protection. Rejected FastAPI (no server-side HTML rendering), Django (too heavy for single-file architecture).
- **WSGI Server:** Gunicorn 21.2.0 with `--workers 8 --timeout 120`. Workers increased from 4→8 for concurrency. No async server (Uvicorn/Hypercorn) because Flask is sync and SQLite is not async-safe.
- **Primary Database:** SQLite with WAL mode, `check_same_thread=False`, and `busy_timeout=5000`. `SQLITE_DB_PATH` env var is **required in production** (raises `RuntimeError` if unset outside development). Default dev path: `data/scheduler.db`.
- **Database Abstraction:** `db_conn()` function returns either a SQLite connection or a PostgreSQL `PooledConnection` wrapper based on `DATABASE_TYPE` env var. Both use context manager (`with db_conn() as conn`) pattern throughout.
- **PostgreSQL path:** Optional upgrade using `psycopg2-binary==2.9.9` and `ThreadedConnectionPool(minconn=2, maxconn=20)`. Activated via `DATABASE_TYPE=postgresql` + `DATABASE_URL`. Migration script: `migrate_to_postgresql.py`.
- **Auth:** Session-based auth using `werkzeug.security` password hashing. No JWT, no OAuth. Roles: `user`, `scheduler`, `approver`, `admin`. Admins automatically satisfy any role check via `has_role()`.
- **Templating:** Jinja2 (built into Flask). Server-side rendering only — no React, Vue, or SPA. Rejected client-side frameworks to keep deployment simple and avoid a build step.
- **CSS:** Single `static/styles.css` file with CSS custom properties for theming (light/dark). CSS Grid for form layouts. No Tailwind, Bootstrap, or preprocessors — rejected to avoid build tooling.
- **JavaScript:** Vanilla JS inline in templates. No bundler, no npm. Rejected any JS framework for same reasons as CSS frameworks.
- **Mission ID format:** Julian date prefix + 3-digit sequence: `YYYYDDD-NNN` (e.g., `2026056-001`). Generated by `next_mission_id(conn, flight_date)` at insert time. Never user-supplied.
- **Deployment:** Docker Compose (single service) for local/on-prem. `manifest.yaml` for Kubernetes. Image: `flt-scheduler:<version>`. Data persisted via volume mount at `/app/data`.
- **Versioning:** Semantic versioning in `VERSION` file (`0.MINOR.PATCH-beta`). Read at startup; embedded in footer and `/health` endpoint. CHANGELOG.md maintained alongside.
- **Backups:** Automatic SQLite backup on startup and daily (7-day rotation). `data/backups/` directory. Backup files never overwrite live DB without explicit restore step.
- **Audit logging:** Every mutation writes to `audit_logs` table via `write_audit()`. Logs older than 90 days are archived to `audit_logs_archive` during daily backup task.
- **SkyVector URLs:** Generated dynamically from `origin`, `route`, `destination` fields using `build_skyvector_url()` — **not stored in the database**.
- **Crew summary field:** The `crew` column in `flights` is a denormalized summary string built by `build_crew_summary()` at insert/update time. It is redundant with `pic_name`, `pilot_name`, `crew_members`, `non_rated_crew` but kept for the Upcoming Missions table and CSV export.

## 5. Data Model

### `flights` table
```sql
CREATE TABLE flights (
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    mission_id        TEXT,                              -- e.g. "2026056-001"
    flight_date       TEXT NOT NULL,                     -- "YYYY-MM-DD"
    launch_time       TEXT NOT NULL,                     -- "HH:MM"
    recovery_time     TEXT NOT NULL,                     -- "HH:MM"
    mission_type      TEXT NOT NULL CHECK (mission_type IN ('training', 'mission')),
    mission_title     TEXT NOT NULL,
    tail_number       TEXT NOT NULL,
    origin            TEXT NOT NULL,                     -- ICAO code
    route             TEXT DEFAULT '',                   -- waypoints string, optional
    destination       TEXT NOT NULL,                     -- ICAO code
    crew              TEXT NOT NULL,                     -- denormalized summary
    pic_name          TEXT DEFAULT '',
    pic_is_amc        INTEGER NOT NULL DEFAULT 0,        -- boolean
    pilot_name        TEXT DEFAULT '',
    crew_members      TEXT DEFAULT '',                   -- free text, comma-separated
    non_rated_crew    TEXT DEFAULT '',
    is_team_flight    INTEGER NOT NULL DEFAULT 0,        -- boolean
    amc_mission_id    TEXT DEFAULT '',
    actual_takeoff    TEXT DEFAULT '',                   -- "HH:MM", set at closeout
    actual_arrival    TEXT DEFAULT '',                   -- "HH:MM", set at closeout
    closeout_comments TEXT DEFAULT '',
    closed_out        INTEGER NOT NULL DEFAULT 0,
    closed_at         TEXT DEFAULT '',
    cancel_weather    INTEGER NOT NULL DEFAULT 0,
    cancel_maintenance INTEGER NOT NULL DEFAULT 0,
    cancel_other      INTEGER NOT NULL DEFAULT 0,
    cancel_other_text TEXT DEFAULT '',
    status            TEXT NOT NULL CHECK (status IN ('planned', 'approved', 'cancelled')) DEFAULT 'planned',
    notes             TEXT DEFAULT '',
    deleted           INTEGER NOT NULL DEFAULT 0,        -- soft delete flag
    deleted_at        TEXT DEFAULT '',
    atp_company       TEXT NOT NULL CHECK (atp_company IN ('A Co', 'B Co', 'C Co')) DEFAULT 'A Co'
);
```

### `users` table
```sql
CREATE TABLE users (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    username      TEXT NOT NULL UNIQUE,
    password_hash TEXT NOT NULL,
    role          TEXT NOT NULL CHECK (role IN ('user', 'scheduler', 'approver', 'admin')),
    active        INTEGER NOT NULL DEFAULT 1
);
```

### `crew` table
```sql
CREATE TABLE crew (
    id     INTEGER PRIMARY KEY AUTOINCREMENT,
    name   TEXT NOT NULL UNIQUE,
    active INTEGER NOT NULL DEFAULT 1
);
```

### `aircraft` table
```sql
CREATE TABLE aircraft (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    tail_number TEXT NOT NULL UNIQUE,
    model       TEXT DEFAULT '',
    active      INTEGER NOT NULL DEFAULT 1
);
```

### `audit_logs` / `audit_logs_archive` tables
```sql
CREATE TABLE audit_logs (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,

    entity_id     TEXT NOT NULL,   -- flight id or "bulk"
    actor_username TEXT NOT NULL,
    details       TEXT DEFAULT '',
    created_at    TEXT NOT NULL    -- "YYYY-MM-DD HH:MM"
);
-- audit_logs_archive has same columns plus:
--   archived_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
```

### `app_settings` table
```sql
CREATE TABLE app_settings (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
    -- current keys: 'ui_theme' ('light'|'dark'), 'timezone'
);
```

### Role hierarchy (Python)
```python
def has_role(user, *roles) -> bool:
    return bool(user and user["active"] and (user["role"] in roles or user["role"] == "admin"))
# admin > approver > scheduler > user
# Admins satisfy ALL role checks automatically.
```

### CSV import format (19 columns)
```
flight_date, launch_time, recovery_time, mission_type, mission_title,
atp_company, tail_number, aircraft_model, origin, route, destination,
pic_name, pic_is_amc, pilot_name, crew_members, non_rated_crew,
is_team_flight, amc_mission_id, notes
```
- Header row optional (auto-detected)
- `mission_id` is auto-generated; do not include in CSV
- Unknown crew names and tail numbers are **auto-created** during import
- All imported flights start as `status = 'planned'`

## 7. Constraints and Preferences

- **Single-file backend.** All Python lives in `app.py`. Do not create new Python modules or packages. The file is large (~2,700 lines) but it is intentional — it keeps deployment trivial.
- **No new dependencies without discussion.** `requirements.txt` is locked to exact versions. Any new library needs a reason.
- **No comments unless the WHY is non-obvious.** Never explain what code does. One-line comments only when a hidden constraint or workaround exists.
- **No build steps.** No npm, no webpack, no SASS compilation. All frontend is plain HTML/CSS/JS that can be served directly.
- **No error handling for internal invariants.** Don't wrap things in try/except that can't actually fail. Only catch at system boundaries (file I/O, DB, network).
- **Database writes always go through `db_conn()` context manager.** Never call `conn.commit()` manually — the context manager handles it.
- **Always pass `conn=conn` to `write_audit()` inside an open `with db_conn()` block** to avoid a second connection opening inside an existing transaction.
- **Version files that must be updated together:** `VERSION`, `Dockerfile` (`ARG VERSION=`), `flt-scheduler` docker-compose (`${VERSION:-...}` appears twice), `CHANGELOG.md`.
- **Left-aligned layout.** The `.layout` CSS class uses `margin: 0` (not `margin: 0 auto`). Do not center the page.
- **Form section headers** use class `form-section-header` with `grid-column: 1 / -1`.
- **Python 3.12**, Flask 3.0.3, Gunicorn 21.2.0, psycopg2-binary 2.9.9, pytz 2024.2, Flask-WTF 1.2.1.
- **No test suite currently exists.** Do not add one unless explicitly requested. Validate features by building the Docker image and hitting the live app.
- **Rebuild and deploy to test.** The canonical test command is:
  ```bash
  docker compose -f flt-scheduler build && docker compose -f flt-scheduler down && docker compose -f flt-scheduler up -d
  ```
